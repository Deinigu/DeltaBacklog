## 1. Overview and principles

DeltaBacklog replaces a NocoDB table of videogames with a small purpose-built app. It runs on a **Raspberry Pi 3B+ (armv7, about 900MB RAM shared with other containers)**, and the phone is the main client.

```
 phone / PC browser
   │  HTTP (LAN only, no login; a reverse proxy may publish it under /backlog/)
   ▼
 ┌─────────────────────────────── one Go binary ───────────────────────────────┐
 │  web/           embedded static PWA (go:embed): index.html, js/*.js, css    │
 │  internal/api   JSON API + /covers/* + /screenshots/*  ──►  internal/db     │
 │       │                                   (SQLite, WAL, one connection)     │
 │       ├──► internal/meta         IGDB, SteamGridDB, link resolver           │
 │       ├──► internal/collections  IGDB collections, upcoming dates, similar  │
 │       ├──► internal/deals        IsThereAnyDeal prices                      │
 │       ├──► internal/hltb         HowLongToBeat times (fragile, optional)    │
 │       ├──► internal/covers, posters   download, resize to JPEG, store       │
 │       └──► internal/shots        screenshot files (originals + thumbnails)  │
 └─────────────────────────────────────────────────────────────────────────────┘
   data/app.db   the whole database      data/covers/   covers (<id>.jpg), posters (p<id>.jpg),
   data/screenshots/ (or SCREENSHOTS_DIR) the owner's pictures                  series/similar posters (i<igdb id>.jpg)
```

Principles that shape every decision:
- **Light.** One static binary, pure-Go SQLite (`modernc.org/sqlite`, no CGO, so cross-compiling is trivial), vanilla JavaScript with **no build step and no framework**. The whole library (about 600 games) is sent to the browser in one JSON response and filtered there, so filtering is instant.
- **Mobile first.** Design for 390px, then scale up. Tap targets of at least 44px, no horizontal page scroll, no hover-only actions.
- **Own the data.** Covers are downloaded once and served from the Pi; the app keeps working when IGDB or SteamGridDB are unreachable.
- **Normalized data.** Every repeated value lives in one row of a lookup table. Nothing is stored as comma-separated text.
- **User choices.** No ratings and no "number in the series". Do not add them back.

## 3. Running it

Go 1.27 and Node 20+ must be on your PATH (Node is only for the frontend tests and the screenshot tool).

```sh
gofmt -l .                         # must print nothing (CI fails otherwise)
go vet ./... && go test ./...
node --test web/test/*.test.mjs
go run ./cmd/deltabacklog          # :8081, data in ./data, keys from ./.env
```

`web/static` is compiled into the binary: **restart after any frontend change**.

**Demo library** (to try the app or take screenshots without your own data; 40 well-known games with generated placeholder covers, add `-env <your .env>` to download real ones):

```sh
go run ./docs/tools/demo-data -data /tmp/demo
LISTEN_ADDR=127.0.0.1:18090 DATA_DIR=/tmp/demo go run ./cmd/deltabacklog
```

**Configuration** (`.env` in the working directory, or real environment variables, which win; `.env` is git-ignored, `.env.example` is committed):

| Variable | Meaning |
|---|---|
| `LISTEN_ADDR` | default `:8081` |
| `DATA_DIR` | default `./data` (holds `app.db` and `covers/`) |
| `SCREENSHOTS_DIR` | where screenshots are stored; default `$DATA_DIR/screenshots` (created at start-up). **When set, the program never creates this folder**, only the per-game subfolders inside it: see "Screenshots" in section 5 and the external drive in section 11 |
| `SCREENSHOT_MAX_MB`, `SCREENSHOT_REQUEST_MAX_MB` | largest accepted screenshot (default 25) and largest upload request (default 200) |
| `SCREENSHOTS_DECODE_BUDGET_MB` | most memory the server may need to decode one screenshot for its thumbnail (default 48); bigger pictures need the browser's own thumbnail |
| `ALLOWED_HOSTS` | extra `Host` names, comma separated (see "Security" in section 5); empty by default. Needed for a router, Tailscale or reverse-proxy name (otherwise 421) |
| `PUBLIC_NAME` | **not read by the program**: `deploy/install.sh` reads it from `/etc/deltabacklog.env`. `off` disables the `deltabacklog.local` name and the port 80 rules, for an app reached only through a reverse proxy (section 11) |
| `SHOTS_MIN_FREE_GB` | **not read by the program**: `deploy/backup.sh` passes it to `backup-screenshots --min-free-gb` (default 5) |
| `IGDB_CLIENT_ID`, `IGDB_CLIENT_SECRET` | a Twitch developer application; enables lookups |
| `STEAMGRIDDB_API_KEY` | enables SteamGridDB covers |
| `ITAD_API_KEY` | an IsThereAnyDeal API key (isthereanydeal.com/apps); enables the Deals page. Sent only in the `ITAD-API-Key` header to `api.isthereanydeal.com`, never logged or put in a URL. **On the Pi it must be in `/etc/deltabacklog.env`** (`deploy.sh --env <file>` copies it from a `.env`; otherwise add the line and restart the service) |
| `GOMEMLIMIT` | Go soft memory limit (for example `96MiB`). The runtime reads it only from the real environment at start-up, so `loadDotEnv` applies a value found in `.env` itself with `debug.SetMemoryLimit` |

`.env.example` lists every setting above with an empty value and a one-line comment. Without keys the app works; lookups answer `configured: false`, the pages that need a key say they are not set up, and the UI offers manual entry. `DELTABACKLOG_LIVE=1` (tests only) switches on the live checks of section 9.
The version printed at start-up and in the usage text is `main.version` (`dev` by default); the release workflow sets it from the tag with `-ldflags "-X main.version=<tag>"`, and `deploy/third-party-licenses.sh` writes the `THIRD_PARTY_LICENSES.txt` that goes into each release archive.

**Port 8081 may be a real, live server (it is the default port).** Test servers must use another port (for example `LISTEN_ADDR=127.0.0.1:18090`), be addressed as `127.0.0.1:<port>` (never `localhost`) and never receive writes aimed at 8081. See `CLAUDE.md`.

**Other commands:** `deltabacklog` with any other first argument than `backup`, `backup-screenshots`, `check`, `sync-igdb` or `fetch-posters` prints usage and exits 2 (a typo never starts the server); `deltabacklog backup <file>` writes a consistent copy of `$DATA_DIR/app.db` exactly as it is (it never migrates it, so a newer binary can back up an older database before upgrading it, and a missing database is an error, never a new empty one); `deltabacklog check <file>` verifies a database or backup read-only (exit code 1 when it is damaged or empty); `deltabacklog backup-screenshots <dir>` copies the files of `SCREENSHOTS_DIR` that `<dir>` does not have yet (same relative paths, through a temporary name; it never overwrites or deletes anything in `<dir>`, and a missing screenshot folder is not an error).

**Importing from NocoDB:** see the README ("Import from NocoDB"). `cmd/import` is idempotent (keyed by the old row id, stored in `game.source_id`) and re-running it retries failed cover downloads.

## 4. Data model

SQLite, `STRICT` tables, `PRAGMA foreign_keys=ON`, WAL, one connection (`SetMaxOpenConns(1)`).

**Migrations** are numbered files in `internal/db/migrations/`, applied in order inside a transaction and tracked by `PRAGMA user_version`. **Add a new file; never edit an applied one.**

| # | What it does |
|---|---|
| 001 | the schema, seed statuses and tiers |
| 002 | drops `game.rating` (no ratings) and rebuilds `v_game_flat` |
| 003 | `saved_view` and five starter views |
| 004 | `game.cover_updated_at` (the cover's cache key) |
| 005 | drops `game.series_order` and rebuilds `v_game_flat` |
| 006 | IGDB link: `game.igdb_synced_at`, `igdb_checked_at`, `igdb_not_found`, and the `sync_candidate` table |
| 007 | IGDB enrichment: `game.time_to_beat_hastily/normally/completely` (minutes), `game.igdb_enriched_at`, lookup tables `game_mode` and `perspective` with their junctions, and `game_link` (store links) |
| 008 | `game.igdb_series`: IGDB's collection name for a linked game (never shown; the series rule below uses it) |
| 009 | `screenshot`: the per-game gallery (metadata only; the files are on disk, see "Screenshots" in section 5) |
| 010 | rankings: `ranking`, `ranking_tier`, `ranking_entry`; `game.poster_file`, `poster_src`, `poster_updated_at`; copies every per-year tier list into a ranking "Tier list <year>" (see "Rankings" in section 5) |
| 011 | `game.poster_user` (0/1): the poster was chosen by the user, so the automatic makers leave it alone. A separate flag because the `poster_src` CHECK cannot be altered in place, and a chosen image still comes from igdb, sgdb or crop |
| 012 | `game.time_to_beat_src` (`igdb`, `hltb`, `manual`; NULL with no time): where the three times came from, backfilled to `igdb` where a time exists |
| 013 | the Series page's "not registered" games: `game_collection` (every IGDB collection of a linked game), `game.igdb_parent_id` (the IGDB game this one is a version of; 0 = none, NULL = not read), and the tables `igdb_collection`, `igdb_collection_game` and `series_hidden` (see "Series collections" in section 5) |
| 014 | Upcoming: (status `wishlist` too, removed again by 018), `game.first_release_date` / `release_date_format`, and `first_release_date`, `release_date_format`, `platforms` on `igdb_collection_game` (see "Release dates and Upcoming" in section 5) |

**Rules and conventions**
- Lookup values are created on demand with `db.GetOrCreate(tx, table, name)` (case-insensitive; the table name is checked against an allow-list).
- `status.code` (`playing`, `playing_evergreen`, `up_next`, `backlog`, `hold`, `evergreen`, `finished`, `dropped`, `not_interested`) is what the API and the views use; labels are display only.
- **Manual order:** `game.queue_pos` is one global order shared by all views. Reordering takes the ids a view shows in their new order and gives them **the positions those games already occupy** (`SlotOrder` in `internal/api/games_write.go`, `slotOrder` in `web/static/js/order.js`: keep the two in sync), so the other games never move. A game that changes status, or is created, goes to the end (`max(queue_pos)+1`).
- **Years played** are `play` rows. Moving a game to `playing`, `playing_evergreen` or `finished` inserts the current year (`recordCurrentYear`, ignored if present). An explicit `years` list in the same request is applied first, so it cannot erase that year.
- **Themes** are folded by `db.NormalizeTheme` (`"4X (explore, ...)"` becomes `"4X"`) on **every** write path (importer, create, patch).
- **IGDB data is read-only in the app and score-free.** Game modes, perspectives and store links are written only by `sync-igdb --enrich` (there is no UI to edit them); time to beat is the exception (next point); IGDB's aggregated/total rating and hypes are never requested or stored (owner decision). The enrichment never changes `updated_at` (the Stats page reads it).
- **Time to beat has a source.** `time_to_beat_src` says who wrote the three times together: `igdb` (the enrichment), `hltb` (picked from HowLongToBeat in the drawer) or `manual` (typed). `PATCH`/`POST /api/games` take `ttb_hastily`, `ttb_normally`, `ttb_completely` (minutes; `null` or `0` clears one, absent leaves it; integers 1 to 100000, else 400; merged with the stored ones) and optionally `ttb_source` (`hltb` or `manual`, the default). Clearing all three clears the source. The enrichment writes only where the source is NULL or `igdb` (and then sets `igdb`), so an owner's or HowLongToBeat's times are never overwritten; relinking IGDB clears only `igdb` times. No HowLongToBeat scores, review or poll counts are requested or stored.
- **Changing the IGDB link clears the enrichment.** A `PATCH` that gives a game another `igdb_id`, or `0`/null, sets `igdb_enriched_at`, `igdb_series` and `igdb_parent_id` to NULL, deletes the game's `game_collection` rows (and `time_to_beat_*` too, unless the owner or HowLongToBeat set them) and deletes the game's `game_game_mode`, `game_perspective` and `game_link` rows in the same transaction (applyFieldEdits): that data belonged to the old IGDB game. The same id again clears nothing.
- **`igdb_id`** links a game to IGDB (unique). A patch that would give one id to two games answers 409 and applies nothing.
- **Cover cache key:** `cover_updated_at` changes only when the image changes and has millisecond resolution (`%f`), so two changes in one second get different versions. `updated_at` changes on every edit and must not be used as a cache key (editing a game would re-download its cover).
- `title_sort` (`db.TitleSort`) lowercases, drops a leading article and punctuation.

## 5. HTTP API

JSON in and out. Errors are `{"error": "..."}` with a status code (every handler and the guard; only a path or method no route knows gets Go's plain-text 404/405). Request bodies are size-limited. There is no authentication: the app is for the home network only.

**Security.** `protect` in `cmd/deltabacklog/guard.go` wraps the root handler (tests in `guard_test.go`). In order: (1) the `Host` header must be an IP literal, `localhost`, `deltabacklog.local`, the machine hostname, `<hostname>.local` or an `ALLOWED_HOSTS` name, else 421 (DNS rebinding); `GET`/`HEAD /healthz` is exempt; (2) `http.CrossOriginProtection` rejects cross-origin unsafe requests with 403 (browsers send `Sec-Fetch-Site`/`Origin`; curl and the app itself pass); (3) POST/PUT/PATCH under `/api/` need `Content-Type: application/json`, else 415, **except** `POST /api/games/<id>/screenshots`, the one route that takes `multipart/form-data` (`isShotUpload`; every other route still answers 415 to it, and step 2 already refused other sites). Every frontend write must send that header (`send`/`request` in `api.js`, the tier list `PUT` in `yearpage.js`). There is still no authentication; see `SECURITY.md`.

| Method and path | Purpose |
|---|---|
| `GET /api/games` | every game with its links (see below) |
| `GET /api/facets` | filter values with counts: `status` (key, label, color, count), `platform`, `genre`, `theme`, `mode`, `perspective`, `player`, `ownership`, `series`, `year` |
| `POST /api/games` | create a game |
| `PATCH /api/games/{id}` | change any editable field |
| `DELETE /api/games/{id}` | delete (204); links, plays and the cover file go with it |
| `POST /api/games/reorder` | body `[id, id, ...]` in the desired order; answers `{id: position}` |
| `POST /api/games/{id}/cover` | body `{"url": ...}` replaces the cover |
| `POST /api/games/{id}/poster` | body is exactly one of `{"url"}` (an allowed host, fetched with `covers.FetchPosterStrict`), `{"crop": true}` (centre crop of the wide cover; 422 when there is none) or `{"auto": true}` (the automatic sources again, replacing a user poster only when one is found). `url` and `crop` set `poster_user = 1`, `auto` sets 0. Answers the game; 400 for a bad body or host, 404, 502 when the download or the services fail (the old poster stays). Bumps `poster_updated_at` |
| `GET /api/lookup?q=` | IGDB search: `{configured, query, results:[candidate]}` |
| `GET /api/igdb/{id}` | one IGDB game as a quick-add candidate (the Series page's Add opens the form from it); `400` bad id, `404 {error}` when IGDB does not know it, `502` when IGDB fails, `503` without keys |
| `GET /api/series/missing` | the cache only, never IGDB: `{configured, owned_roots:[igdb id], series:[{key, collections:[{id,name,fetched_at}], missing:[game], hidden:[game]}], refresh:{running, done, total, finished_at?, report?, failed?}}` where a game is `{igdb_id, title, year or null, cover or null, v, parent, collection_id, date or null, format or null, platforms or null}` (`date` is IGDB's first release date in unix seconds UTC, `format` its date_format: 0 day, 1 month, 2 year, 3-6 quarter, both null when IGDB has none, `platforms` is "PC, PS5"; `cover` is a file under `/covers/`, `v` IGDB's image id for the URL's `?v=`, `parent` the root of its version chain or 0). `key` is the series name trimmed and lower-cased. Games the library owns (their whole IGDB version family, see below) are left out, so an added game vanishes at once |
| `POST /api/series/refresh` | starts the background refresh (below) and answers `202` with its status; a second call while it runs just answers the status. `503` without IGDB keys |
| `POST /api/series/hide`, `POST /api/series/unhide` | body `{collection_id, igdb_id}`; `404` when that game is not in the cached collection, `400` for a bad body |
| `GET /api/similar` | the cache only, never IGDB: `{configured, suggestions:[{igdb_id, title, year or null, cover or null, v, parent, date or null, format or null, sources:[igdb id], hidden}], owned_roots:[igdb id], fetched_at, refresh:{running, done, total, finished_at?, report?, failed?}}`. One query for the suggestions (the cached games the library does not own, whole family), hidden ones flagged; `fetched_at` is the oldest source read (`""` before the first refresh) |

**Game (read model):** `id, title, status` (code)`, ownership, series, developer, release_year, vr, favorite, completed, notes, cover` (file name)`, queue_pos, igdb_id, added_at, updated_at, cover_v, platforms[], genres[], themes[], players[], years[]` (calendar years, ascending)`, periods[]`, time to beat: `ttb_hastily, ttb_normally, ttb_completely` (minutes or `null`) and `ttb_source` (`igdb`, `hltb`, `manual` or `null`), and from the IGDB enrichment (empty until it ran): `modes[]`, `perspectives[]`, `links[]` (`{kind: steam|gog|epic|official, url}`).

**`PATCH /api/games/{id}`** accepts any of: `status, favorite, vr, completed, title, notes, ownership, series, developer, release_year, platforms[], genres[], themes[], players[], years[], periods[], igdb_id`. Absent fields are untouched. Text lookups (`ownership, series, developer`) clear with `""`, numbers (`release_year`, `igdb_id`) with `0`, lists replace the whole set (`years` only the calendar years, `periods` only the periods). Validation: non-empty title (at most 200 characters), `release_year` 1950 to 2100, `years` 1970 to 2100, `periods` of `childhood` or `always`, at most 50 list items, names at most 120 characters. Answers the updated game, `400` for invalid input, `404`, or `409` for an `igdb_id` that another game has.

**`POST /api/games`** takes the same fields as `PATCH` (including `years`, `periods`, `players`, `favorite`, `vr`, `completed`, `notes`; years picked by the client and the current year recorded for Playing/Evergreen/Finished merge without duplicates) plus `cover_url` (and requires `title`; `status` defaults to `backlog`). Answers `201 {"game": {...}, "cover_error": ""}`; a cover that fails to download does **not** fail the creation (the message is in `cover_error`). `409 {"id": <existing>}` when the `igdb_id` already exists.

**Screenshots** (`internal/api/screenshots.go`, `internal/shots`). The original is stored byte for byte (nothing stripped) as `<SCREENSHOTS_DIR>/<game id>/<32 hex>.<jpg|png|webp>` next to a 480px JPEG thumbnail `<32 hex>_t.jpg`; the name is random, never the client's. Upload: `MultipartReader` streams each part to a temporary file (no buffering in memory; `MaxBytesReader` caps the request), the type is decided by sniffing the first bytes (JPEG, PNG, WebP; SVG, HTML, GIF and the rest are refused whatever the name or `Content-Type` says), `image.DecodeConfig` reads the size (a hard sanity cap of 250 MP, computed in `int64`), and `shots.DecodeCost` estimates the peak memory of decoding the whole picture from that plus a tiny header parse: a JPEG costs one byte per sample (4:2:0 is 1.5 B/px, 4:4:4 is 3, a 4-component one, or a 3-component one stored as RGB (Adobe transform 0, or component ids R, G, B), adds 4 B/px for the extra RGBA/CMYK image) and a progressive one adds 4 bytes per sample for its coefficient blocks; a PNG costs 1, 2, 4 or 8 B/px by colour model (16-bit RGBA is 8); a WebP 4. Measured on a 40 MP JPEG: baseline 4:2:0 about 60 MB, progressive 4:2:0 about 285 MB, progressive 4:4:4 about 570 MB (the Pi's `MemoryMax` is 160 MB). **Budget:** `SCREENSHOTS_DECODE_BUDGET_MB` (default 48). Within it, **one image at a time** (`decodeMu`) is decoded and drawn with `draw.ApproxBiLinear` into a fresh small RGBA (`draw.BiLinear` allocates a scratch buffer of cropped height x 480 x 32 bytes that the estimate does not count: 148 MB for a 47 MP grayscale JPEG) that fits in 480x960 (a picture taller than 1:2 or wider than 4:1 is centre-cropped to that ratio; the grid uses `object-fit: cover`). Over it, the untouched original is still stored but the server does not decode it: the browser makes the thumbnail (`createImageBitmap` with `resizeWidth`, then a canvas JPEG of at most 480x960) and sends it as a `thumb` part after the `file` part; `shots.WriteClientThumb` accepts it only if it is a JPEG of at most 512 KB and 480x960 that decodes (cheap at that size). Without a valid `thumb` part the file is removed and the result says it is too big to preview here. The refusal result carries `needs_thumb: true` with the picture's `width` and `height` (as shown, EXIF applied); the UI then makes the thumbnail with the same crop rule as the server (`thumbPlan` in `shots.js`, kept in sync with `thumbPlan` in `shots.go`), using `createImageBitmap` with a source rectangle and a target size so the browser never builds a big bitmap, and sends the file again with the `thumb` part (an API client can send the `thumb` part right away; the server ignores it when it can make its own). If the browser cannot make one the user is told so. EXIF (JPEG only, `exif.go`): orientation (applied to the thumbnail; the browser applies it to the original) and `DateTimeOriginal` (`taken_at`, no zone); without EXIF `taken_at` is the file's last-modified time sent by the client. Serving accepts only names matching `shots.NameRE`, so no path trick reaches another file; both kinds get `X-Content-Type-Options: nosniff` and a one-year immutable cache (names never change content). Deleting a game removes `<SCREENSHOTS_DIR>/<id>/` after the transaction committed; deleting one screenshot removes its two files. **Storage rule:** `shotStorageOK` needs `SCREENSHOTS_DIR` to exist as a folder and be writable (a probe file) at every upload and every delete (a delete answers 503 before touching the row, so no file is orphaned); the list request uses `shotStorageReadable`, which only checks the folder and `access(W_OK)` (no write, so opening a drawer does not wake an idle drive). A game's folder is created only after the content passed the type check, so a refused upload leaves no empty folder. At start-up, when the storage is available, `SweepShots` tidies the numeric game folders, touching only files older than an hour and **never deleting an original** (after a database restore the drive may hold the only copy of pictures the older database does not list): it removes `*.tmp` files and thumbnails whose original is gone; an original without a row whose game exists is **re-adopted** (a row is inserted again from `Inspect`: size, EXIF date; the thumbnail is made again if it is missing and the picture fits the decoding budget, otherwise it shows as "Missing"); an original of a game this database does not know (or a file that is not a readable image) is **moved** with its thumbnail to `<SCREENSHOTS_DIR>/.orphans/<game id>/`. The sweep stops at the first database error, so an incomplete list of rows can never turn pictures into orphans. Anything else on the drive is left alone, and the result is logged. Limits of re-adoption: game ids are reused (no AUTOINCREMENT), so a file is adopted only if its modification time is not older than the game's `added_at` minus 10 minutes (a picture cannot predate its game); an older one belongs to an earlier game with that id and is moved to `.orphans/`. The adopted picture's `taken_at` is the EXIF date or else the file's modification time (the upload time, not the photo's date). An over-budget original whose thumbnail file was lost keeps showing "Missing": nothing regenerates it, because only the browser can make that thumbnail (upload it again if it matters). `WriteThumb` runs `runtime.GC()` before it releases `decodeMu`, so two decodes in a row never keep two bitmaps in the heap. The browser makes the thumbnail before the upload for files over 8 MB (`BIG_UPLOAD`, size read with an `Image`), so a big photo is sent once; the `needs_thumb` retry remains for smaller files that still exceed the budget. The server never creates `SCREENSHOTS_DIR` itself, only the per-game subfolders; `main` creates it only for the default `$DATA_DIR/screenshots`. So an external drive that is not mounted (an empty mount point on the SD card, or a path that does not exist) can never fill the SD card: uploads answer 503 "screenshot storage not available", the list says `available: false` (the drawer shows a notice and missing thumbnails show "Missing"), and everything else keeps working. At start-up a warning is logged.

**Rankings** (`internal/api/rankings.go`, migration 010). Validation: name and tier label 1 to 80 characters (trimmed), description up to 500, colour `#rrggbb` (stored lower case), at most 200 rankings, 30 tiers per ranking, 2000 games per ranking; every JSON body is limited (64KB, 4KB for tiers, 256KB for the board). Positions are only an order (gaps allowed, ties broken by game id); the endpoints that move things rewrite the affected lists densely. `ranking_entry.tier_id` must belong to the same ranking: the API checks it (the foreign key only knows the table). Deleting a tier first appends its entries to the pool, then deletes the tier. **`PUT .../board` is deliberately partial** because the editor saves through a debounced queue and other requests (adding a tier or a game) can overtake a save: it only touches what it lists. A tier it does not list keeps its place (and is moved after the listed ones in the order), a game it does not list stays in its tier after the listed games, a game id that is not in the ranking is ignored (a game removed meanwhile is not resurrected), and so is a tier id that no longer exists (a delete overtook the save; its games are already in the pool), but a tier id that belongs to another ranking, a game listed twice, a bad label or colour, or a missing key is a 400 and changes nothing. Tiers are added and deleted only through their own endpoints, never by the board save. The old tier list endpoints (`/api/tierlist/{year}`) are gone.

**Series collections** (`internal/collections`, `internal/meta/collections.go`, `internal/api/series.go`, migration 013). The Series page lists, per series, the games of its IGDB collection that the library lacks. *Mapping:* a user series is not matched by name; its linked games decide. Every IGDB collection of a linked game is stored (`game_collection`, written by the enrichment on every `--enrich` run, also `--refresh`, and by the collections refresh for games the enrichment has not read; cleared when the game's IGDB link changes). `pickCollections` then chooses per series: the collection most of its linked games share; on a tie the collection(s) named like the series (equal, or one name contains the other, both at least 4 letters: "Zelda" is the series of "The Legend of Zelda" but not of "Ocarina of Time"); if none, the one(s) named like a game's `igdb_series` (IGDB's first collection of that game, which is arbitrary, so it only decides when the owner's own name matches nothing); if that does not decide either, all the tied ones (the union). So Zelda with Ocarina and Breath of the Wild linked gets the main collection, a series called "Zelda" with only Ocarina linked still gets the main collection, and "Mario Kart" does not get the whole Mario collection. A series whose games are not linked has no collection and lists nothing. *Family:* IGDB splits one game into several entries, related by `parent_game` and `version_parent`: Ace Attorney is a chain, the JP original `221280` <- the DS entry `1426` (an expanded game, in no collection list) <- the 2013 remaster `221285` and a port `221282`. `parent_game` also joins games that are **not** the same game: a standalone expansion (type 4, Uncharted: The Lost Legacy -> Uncharted 4) and a remake (type 8, Resident Evil 2 (2019) -> the 1998 game), and those are separate games the page lists. So `meta`'s `igdbGame.parent()` returns a parent only for `version_parent`, or for `parent_game` when the game's type is 9 (remaster), 10 (expanded game) or 11 (port), and only that parent is ever stored. The refresh (`collections.Refresh`, `resolver`) follows those links up to the **root** (asking IGDB for the links of entries in no collection, up to five levels, memoised for the run) and stores the root: `game.igdb_parent_id` for the library's games (0 = its own root, NULL = not read yet), `igdb_collection_game.parent_igdb_id` for the cached ones. A cached game is owned when its root is the root of an owned game (`family.has`): the original, the expanded entry, the remaster and the port of an owned game are all one family, whichever of them is linked. The server's `owned_roots` list lets the browser apply the same rule to a game added since; a game added through the Series page's Add sends the root with it (`igdb_parent_id` in `POST /api/games`, taken from `GET /api/igdb/{id}`, which walks the chain), so its original goes at once. The enrichment stores the collections and never touches the root (changing a game's IGDB id clears it); the refresh that ends `sync-igdb --enrich` reads it where it is NULL. Nothing is downloaded for owned games. *Cache:* `igdb_collection` and `igdb_collection_game` hold, per picked collection, the games IGDB returns for `where collections = (id) & game_type = (0,4,8,9)` (main game, standalone expansion, remake, remaster; DLC, expansions, bundles, mods, episodes, seasons, expanded editions, ports, forks, packs and updates are dropped, and `meta.IsRealGameType` checks the answer too), up to 1000 per collection in pages of 500, never a score. *Refresh rules:* the cache is only written by `collections.Refresh`: the page's **Refresh from IGDB** (`POST /api/series/refresh`, one background goroutine at a time, 30 minute limit, status polled through `GET /api/series/missing`; the progress counts the collections first and then the posters) and `sync-igdb --enrich` (after the enrichment finished without stopping; not in a dry run). It first reads (`meta.GameLinks`, 40 games per request) the collections and parent of the linked games not read yet, then reads every picked collection, one request each (plus a page per 500 games), then downloads the posters, then (a finished run only) prunes: it deletes the cached collections no series picks, forgets (and deletes the file of) the poster of a game that has become owned, and sweeps `i<id>.jpg` files no row names that are older than ten minutes (the server's refresh and `sync-igdb --enrich` are separate processes on one folder: a younger file may be a download the other process has not recorded yet). Every IGDB request goes through `meta.Client.pace` (4 per second, shared with quick add and posters inside the server), and a 429 is waited out (`Retry-After`, else 2 s doubling, 3 retries) before the run stops with what it has stored; a collection that fails (not 429) is skipped and 5 in a row stop the run. A collection is replaced in one transaction, so a failed read keeps the older list. Opening the page never reads IGDB. *Missing = a cached game of a picked collection that is not owned (family rule above) and not in `series_hidden`*, computed at read time (`collections.Load`, and again in the browser by `missingIndex`), so a game the owner adds disappears without a refresh. Hiding is per (collection, game): `series_hidden` has no foreign key, so a hide survives a collection being read again; the page keeps its own copy of the answer in step (a hide survives `games-changed`). *Images:* the posters of the missing games (not the library's, not the hidden ones) are fetched once, `t_cover_big` from `images.igdb.com` only (`https`, no redirects, 15 MB cap, the covers' 16 megapixel decode cap), centre-cropped to 2:3 and at most 300 px wide (about 15 to 30 KB), stored as `i<igdb id>.jpg` next to the covers (`covers.FetchMissingPosterStrict`; tests replace it through `Server.MissingPosterFetch`, never `PosterFetch`, which writes `p<game id>.jpg`) and served by `/covers/` with `?v=<IGDB image id>` in the URL (the answer's `v`), because covers are cached for a month; the phone never calls IGDB. A poster of a game that left its collection is deleted when no other row uses the file. A refresh on a big library downloads a few hundred posters one after another (one decode at a time, like the poster queue). *Add:* the client asks `GET /api/igdb/{id}` (`meta.GameCandidate`, one request on a tap) and opens the add form with that candidate, with the user's own series name in place of IGDB's; it then posts the usual `POST /api/games` with the `igdb_id`.

**Similar games** (`internal/collections/similar.go`, `internal/meta/collections.go` `SimilarGames`, `internal/api/similar.go`, `web/static/js/similar.js`, `similarview.js`, `similardrawer.js`, migration 015). *Sources:* the library games linked to IGDB that are finished (status `finished`) or a favourite (`sourceSQL`); there is no "outcome" column, the status is the outcome. *Reading:* `RefreshSimilar` first runs `linkLibrary` (the series refresh's step 1: collections and version roots of the linked library games whose `igdb_parent_id` is NULL; a no-op once known), so the family rule holds without a series refresh, then asks IGDB (`meta.Client.SimilarGames`: `fields similar_games.name, ...cover.image_id; where id = (...)`, 40 sources per request, through the shared `pace`) and keeps the real game types only (0 main game, 4 standalone expansion, 8 remake, 9 remaster; `meta.IsRealGameType`, the same filter as the series cache). The root of each suggestion's version chain is resolved with the series cache's `resolver` (`GameLinks` for the parents), so a remaster of an owned game is dropped and a remake or standalone expansion is kept (same `family` rules as `collections.Load`; see Series collections). Each batch is stored in its own transaction: the source's links are replaced, suggestions are upserted keeping `cover_file` while `cover_image` is unchanged, `similar_fetch` is stamped. A 429 is waited out three times (`retry429`), then the run stops with `Report.Stopped` and what was stored stays. *Posters:* first reused from `igdb_collection_game` when the series cache already holds the same image, then downloaded for the best ranked suggestions only (at most 300, most sources first), not for hidden or owned games, as `i<igdb id>.jpg` (`covers.FetchMissingPosterStrict`, host-checked). *Prune* (end of a finished run, `pruneSimilar`): links and fetch marks whose source is no longer a finished/favourite linked game are deleted, then suggestions no link names; a suggestion that has become owned loses its poster; `similar_hidden` is never pruned (a hide outlives the cache). *Shared posters:* the Series and Similar caches share the `i<id>.jpg` files, so every deletion goes through `fileInUse` (any row of `igdb_collection_game` or `similar_game` naming the file keeps it) and the folder sweep (`sweepPosters`, called by both prunes) names the union of both tables and keeps the 10-minute grace for fresh files. *Hide:* its own table keyed by IGDB id (`similar_hidden`), deliberately not `series_hidden` (which is keyed by collection and igdb id): hiding a suggestion does not hide the game on the Series page, nor the reverse. *When it runs:* only by `POST /api/similar/refresh` and `sync-igdb --enrich` (after the series collections); never on a page load. *Frontend:* `similarIndex` (pure) takes the answer and `store.games` and returns `items` (ranked: number of sources desc, then the newest source by latest year played then game id, then year desc, then title), and `hidden`; a game is owned through the roots the server sent or a game added since (IGDB id or parent). Sources shown are recomputed from `store.games` (a game that went back to the backlog stops suggesting at once). Hide uses `setHiddenFlag`, which flips the flag inside the held answer, so the index rebuilt on `games-changed` keeps it (the same job as `moveHidden`). Add calls `GET /api/igdb/{id}` (the candidate with the version root, as on the Series page) and open the add form (status `backlog`). The game drawer's row (`similardrawer.js`) reads `GET /api/similar` once when a source game's drawer opens. **Release dates and Upcoming** (`internal/meta/release.go`, `internal/collections`, `web/static/js/upcoming.js`, `upcomingview.js`, migration 014). *Storage:* `first_release_date` is IGDB's `first_release_date` (unix seconds, UTC) and `release_date_format` the `date_format` of the `release_dates` entry with that same date (the finest one when platforms share the date; TBD is no date, stored as NULL), because IGDB gives a year release a day inside the period (the last day of 2027 for "2027"), so the date is only meaningful with its format; `release_year` is untouched. Both are IGDB's own data and are overwritten, and cleared when the game's IGDB link changes. *Who writes them:* the enrichment (every `--enrich` / `--refresh` run, from `GameDetails`), `POST /api/games`, `PATCH` with an `igdb_id` and `POST /api/link/accept` (one best-effort `meta.ReleaseDates` request each, run in a goroutine after the response so a slow IGDB never delays the request, only when the IGDB link is new or changed, and ignored when IGDB is not set up or fails), `store` (collections package) for the cached collection games (with their `platforms`), and `collections.Refresh` step 3 (`refreshReleases`, only when the source also implements `collections.ReleaseSource`): it reads in batches of 40 the linked library games that have no date, or have a date in the future or less than 90 days old (older dates are final). Nothing reads IGDB on a page load. *Upcoming* has no endpoint of its own: the browser takes the `missing` lists of `GET /api/series/missing` (hidden games are never in them; each game carries `date`, `format` and `platforms`) and `buildUpcoming` groups them by month. `release_date` / `release_format` are also served in `GET /api/games`. Both pages hide a game with the shared `moveHidden` (it moves the entry inside the cached answer, so the index rebuilt on `games-changed` keeps it hidden). Dates use the fixed `en-GB` locale (`LOCALE`), like the rest of the English UI. *Grouping rules:* everything is read in UTC (a release on the 1st stays in its month in every time zone); "today" is the viewer's calendar date; a day counts as out on its day, a month, quarter or year once it is over; out within 60 days goes to "Recently released", older is dropped; a month or day is grouped by month ("This month", "Next month", "March 2027"), a quarter or year gets its own group after the months it covers, and a release starting more than 18 months away, or with no date, goes to "Later / TBA". Tests: `internal/meta/release_test.go`, `internal/collections/release_test.go`, `internal/api/release_test.go`, `internal/db/series_collections_test.go` (migration 014 on a populated database), `web/test/upcoming.test.mjs` (month grouping, precision, TBA, time zones).

**Posters** (`internal/covers/poster.go`, `internal/posters`). A poster is a centre-cropped 2:3 JPEG, at most 300 px wide (never scaled up), stored as `p<game id>.jpg` in the covers folder, so it is served by `/covers/` with the same cache headers, deleted with the game, and cached by the service worker's `covers-v2` cache (keyed by path; an entry is used only when its URL carries the requested `?v=`); `game.poster_file` names it and `poster_updated_at` is its cache key (`poster`, `poster_v` in `/api/games`, `posterURL()` in `api.js`). Sources, in order (`posters.Maker.Make`): (1) the IGDB cover of the game's `igdb_id` (`meta.IGDBCoverURL`, size `t_cover_big_2x`), (2) a SteamGridDB 600x900 static grid for the best title match (`meta.SteamGridPortrait`), (3) a centre crop of the wide cover already on disk (no network). A source that has nothing is skipped; `poster_src` records which one won (`igdb`, `sgdb`, `crop`). A source that **fails for now** (network error, 429, a 5xx, a download that fails to connect) makes `Make` return `ErrTemporary`: no poster is stored, not even the crop, so a later try can find the real one (the queue waits ten times longer and does not retry that game until the program restarts; `fetch-posters` just reports it, run it again). A **permanently bad** download (a 4xx such as 404, a file that is not an image, too large or too small: `covers.ErrBadImage`, `covers.StatusError.Permanent`) does not count as temporary: the next source is tried and then the crop. The crop is only made when the sources really have nothing, or are not configured. Downloads go through the same host allow-list as client-supplied covers (`coverHostAllowed`), `covers.FetchPosterStrict` (no redirects, 15 MB cap) and the same 16 megapixel decode cap as covers. Making them: adding games to a ranking (and opening a ranking) hands the games without a poster to `posters.Queue`, a **single background goroutine** that makes one poster at a time with a pause after each (800 ms; IGDB allows 4 requests a second), never blocks a request, bounded at 1024 waiting games, and remembers games that failed until the program restarts (so a game with no source is not retried on every visit). `GET /api/rankings/{id}` reports `posters_pending`; the editor polls it every 2.5 s, copies the new posters into the loaded games (`applyPosters`, which returns the changed ids) and swaps the picture in those tiles only (`refreshTiles`); the poll never rebuilds the board. When a poster is stored the queue drops the cached `/api/games` response (`OnMade`). `deltabacklog fetch-posters [--dry-run] [--limit N] [--upgrade] [--db path]` makes the poster of every game that has none, one every second (`--upgrade` also redoes the `crop` ones, for example after `sync-igdb` linked more games); `--dry-run` uses no network and writes nothing. **Posters chosen by the user** (`Maker.Choose`, `ChooseCrop`, `Remake`; `POST /api/games/{id}/poster`). The file name stays `p<id>.jpg`, so a new poster overwrites the old file (nothing to clean up, and `deleteGame` removes it as before). A poster the user chose has `poster_user = 1`: `Maker.Make` (the queue) returns `ErrUserPoster`, and `fetch-posters --upgrade` selects only `poster_src = 'crop' AND poster_user = 0`. `Remake` ("fetch automatically again") is the only automatic path that replaces it, and only when a source really delivers; a temporary failure keeps the user's poster. Every maker downloads (or crops) into its own scratch folder `covers/.poster-*` without any lock, so a slow lookup (SteamGridDB blocked, 12 s) never delays a pick. The final step, `Maker.commit`, takes `Maker.mu` and runs a guarded `UPDATE ... WHERE poster_user = 0 OR <override>`; only when it took (`RowsAffected`) is the file renamed over `p<id>.jpg`. "Fetch automatically again" (`Remake`) may replace a user poster only if `poster_updated_at` is still what it read first, so a pick made while it ran wins; the sheet also disables itself (`inert`) while a change is on its way. At start-up `posters.SweepScratch` removes `.poster-*` folders older than 10 minutes that a crash left behind. So an automatic result that lost the race against a pick is refused (`ErrUserPoster`) and never overwrites the user's file, also when the other writer is the `fetch-posters` process (the mutex only orders makers inside one process; the guard covers the rest). A pasted URL is labelled `igdb` when its host contains `igdb`, else `sgdb` (`poster_src` has no other value). Changing the wide cover (`POST .../cover`) never touches the poster, so an automatic `crop` poster keeps the old crop until `fetch-posters --upgrade` or "fetch automatically again". Memory: one image is decoded at a time (a poster source is about 500x750), so the run fits the Pi's `GOMEMLIMIT=96MiB` (measured: 40 games from the crop source, peak working set 64 MB with `GOMEMLIMIT=96MiB`).

**Safety limits** (enforced server-side, covered by tests)
- A client-supplied cover URL (and every poster URL the server fetches) must be on `cdn2.steamgriddb.com`, `cdn.steamgriddb.com` or `images.igdb.com`; redirects are never followed; images larger than 16 megapixels are rejected (computed in `int64` because the Pi is 32-bit).
- A pasted link is only fetched from Steam, GOG, Epic or IGDB, every redirect is re-checked against that list, and the page must answer 200. (The UI no longer advertises links; the resolver remains in `internal/meta`.)
- Screenshots: 25 MB per file and 200 MB per request by default (`SCREENSHOT_MAX_MB`, `SCREENSHOT_REQUEST_MAX_MB`), 50 files and 200 parts per request, decoding budget 48 MB (`SCREENSHOTS_DECODE_BUDGET_MB`), caption 500 characters, order list 64KB.
- Request body limits: 64KB for games, views and rankings, 256KB for reorder and for a ranking board, 4KB for a tier, a cover URL and the link calls.
- `GET /covers/` and any other folder path answer 404: the cover folder is never listed.

### Background jobs and caches

Three jobs read other websites: **Series** and **Upcoming** (IGDB collections, `POST /api/series/refresh`), **Similar games** (IGDB, `POST /api/similar/refresh`) and **Deals** (IsThereAnyDeal, `POST /api/deals/refresh`). They all follow one pattern, so a new one should copy it:

- **Cache-only reads.** The matching `GET` (`/api/series/missing`, `/api/similar`, `/api/deals`) answers from the database and never calls the outside service. Nothing reads a service on a page load. The only automatic outside reads are best-effort, one game at a time: the IGDB details and release date of a game that is added or newly linked.
- **One job at a time per page.** Each has a small job struct in `internal/api` (`seriesJob`, `similarJob`, `dealsJob`: mutex, `running`, `done`, `total`, `finished`, `report`, `failed`). The `POST` starts one goroutine and answers `202` with the status; a second `POST` while it runs just answers the status. `503` when the keys are missing. The jobs are independent of each other (Series/Upcoming share one; Similar has its own). Limits: Series and Similar 30 minutes, Deals 20.
- **Status shape** (in the `refresh` key of the page's `GET`): `{running, done, total, finished_at?, report?, failed?}`. The page polls the `GET` every couple of seconds while `running` is true, so a refresh survives leaving the page. A run stopped by a 429 or a refused key sets `failed` and a `report` the owner can read; what it stored stays.
- **Stale-write guards.** A refresh must never overwrite a newer decision: Deals' `savePrice` stores a price only if the game is still matched to that ITAD id (a match changed meanwhile wins) and owner matches (`source = 'user'`) are never searched again; a series collection is replaced in one transaction, so a failed read keeps the older list; the posters of games that became owned are dropped, and the `i<id>.jpg` files are shared by the Series and Similar caches (`fileInUse`, 10-minute sweep grace); a user-chosen poster (`poster_user`) is never replaced by automatic work.
- **Cache invalidation.** The cached `/api/games` and `/api/facets` responses are dropped by `s.cache.invalidate()` after every write in this process (a job calls it when it ends, because release dates are inside `/api/games`) and when `PRAGMA data_version` changes (a write by another process, such as `sync-igdb` or `fetch-posters` run next to the live service; see "Cache and other processes"). The page answers (`/api/deals` and the others) are not cached.
- **Also from the command line.** `sync-igdb --enrich` runs the Series/Upcoming and Similar refreshes at its end. They are separate processes with their own client, so run them while the server is idle if you want to stay under the rate limits below.

| Service | Pacing in the code | Provider limit and what happens on 429 |
|---|---|---|
| IGDB | `meta.Client.pace`: one request per 250 ms for everything in the process (add, posters, series, similar) | 4 requests per second. A 429 is waited out (`Retry-After`, else 2 s doubling, 3 to 6 retries), then the run stops with what it stored |
| IsThereAnyDeal | 400 ms between requests; prices 50 games per request | 1000 requests per 5 minutes. A 429 becomes `RateLimitError`; the refresh stops with what it saved |
| SteamGridDB | a few requests per cover/poster pick | no documented hard limit; sometimes blocked by providers, the poster sheet then says so and IGDB's options still show |
| HowLongToBeat | searches at least 1 s apart, 8 s timeout | no API; may block or change. Never retried in a loop |

## 6. Backend packages

- **`internal/db`**: `Open` (pragmas, single connection, migrations), `Migrate`, `GetOrCreate`, `IndexGame` (refresh one FTS row), `TitleSort`, `NormalizeTheme`.
- **`internal/importer`**: `Import(db, csv, options)` splits comma lists (respecting parentheses), parses `Years_played` (`2025,2026`, `Childhood`, `Always`), maps the NocoDB attachment JSON to a cover URL, and returns a report with warnings plus the list of covers to download.
- **`internal/api`**: handlers use a small `pathID`, `writeJSON`/`writeJSONStatus` (content type is set **before** the status) and `writeErr`. `LoadGames` builds the whole read model with one query per link table. `applyFieldEdits` is the single place that writes editable fields (used by patch and create), inside the caller's transaction, and re-indexes the FTS row.
- **`internal/meta`**: `Client` with overridable base URLs (so tests use local fakes). IGDB access tokens are cached until just before they expire. `SearchIGDB` (asks IGDB for 50 hits plus the games named exactly like the query, `where name ~ "title"`, merges them and returns them ranked by `RankCandidates` (every exact-name game, never cut, plus up to 30 other hits; the exact-name query asks IGDB for up to 200 games, the search for 50, so "Pac-Man" with over 50 namesakes is complete and the response stays at a few hundred kilobytes): exact name first, then games released in the year hint, then, among namesakes, DLC, bundles, mods, episodes, packs and updates last (demoted, never dropped), then the number of `external_games` ids (store ids; used only for ordering, never stored or shown, not a score), then `game_type` tier (main game, standalone expansion and expanded game; remake and remaster; port), then older first. Other hits keep IGDB's order. The sync classifies against the whole list, because a safe link must see every namesake. Only quick-add shortens it, with `TopResults`: 12 results, at most 6 of them exact namesakes, so a franchise name (Doom, Tetris) still shows its sequels. A trailing year, `God of War 2005` or `Portal (2007)`, is split off by `SplitYear` and is a ranking hint; both the whole title and the title without the year are searched and asked as exact names (`FIFA 2003` is `FIFA Soccer 2003` on IGDB). If an extra query fails with anything but 429 or a cancelled request, the hits already collected are kept. `Client.IGDBGap` (default 250 ms) paces every IGDB request through one shared limiter per `Client`, so within one process quick-add, posters and the sync together stay under IGDB's 4 requests per second (the `sync-igdb` and `fetch-posters` commands are separate processes with their own client, so running one while the server is busy can exceed it; the sync backs off on 429). The IGDB sync uses the same function. When the main pass finds nothing it retries with a `where alternative_names.name ~ *"title"*` query, then the part before `:` or `-`, then the title without spaces, which rescues localized titles and spacing differences), `IGDBImages` (artworks and screenshots with their real sizes, then the box cover), `SearchCovers` (SteamGridDB, wide shapes first), `IGDBPosters` and `SearchPosters` (the portrait options of the poster sheet), `ResolveLink`. A non-200 answer is a `*meta.HTTPError` (the sync reads its `Status` to back off on 429). `TitleScore(a, b)` rates two titles 0 to 100 ignoring case, accents, punctuation, a leading "the" and roman numerals; titles with different numbers ("Resident Evil 2" and "3") are capped at 59, and a title that starts the other ("Dark Souls III" and "... The Ringed City") scores at least 75.
- **`internal/igdblink`**: the IGDB sync (see section 8). Phase 2 is `enrich.go`: `Enrich` reads the linked games from IGDB in batches (`meta.Details`, `meta.TimeToBeat`) and `enrichGame` stores one game inside the batch's transaction. Phase 1: `Classify` sorts one game's IGDB results into *confident* (exactly one candidate with `meta.TitleScore` >= 90 **and** a shared platform), *uncertain* (best score 60 to 89, no shared platform, or several equally good candidates; at most five stored) or *not found*. A candidate is scored against its name and its IGDB alternative names (localized titles), whichever is best. When several candidates are strong, a single one whose name equals the title exactly (`meta.SameName`: case and accents folded, "the" kept) wins. Uncertain and not-found games also keep IGDB's first three results as weak proposals (score under 60 is greyed in the UI), because they cost nothing and save a manual search. `db.FileURI` escapes `%`, `#` and `?` in database paths (they would otherwise be read as URI query or fragment). `Run` is the resumable runner (single goroutine, paced by the meta client's 250 ms between IGDB requests (no pause of its own), doubling backoff on 429), `Queue`/`Accept`/`NotOnIGDB` are the review queue, `Main` is the `sync-igdb` command (`--enrich` runs phase 2). Only the link is stored: no IGDB scores or ratings.
- **`internal/shots`**: `Sniff` (magic bytes), `Inspect` (type, size, pixel cap, EXIF), `WriteThumb`, `NameRE`, `SyncNew` (the incremental copy behind `backup-screenshots`: copies files missing from the destination through a temporary name, never overwrites or deletes). `exif.go` reads only the APP1 segment and returns defaults on anything odd.
- **`internal/collections`**: `Refresh` (reads the IGDB collections of the library's series into the cache and downloads the missing games' posters; `Source` is the small IGDB interface it needs, satisfied by `*meta.Client`), `Load` (the cached games per series, minus what the library has and what is hidden), `Hide` and `Unhide`. See "Series collections" in section 5.
- **`internal/deals`**: the IsThereAnyDeal client (`Client`, behind the small `Source` interface the refresh and the tests use) and the cache logic (`store.go`). The client calls only `api.isthereanydeal.com` (loopback is allowed so tests can use a fake server), refuses redirects, caps answers at 8 MB, paces requests (400 ms apart) and turns a 429 into `RateLimitError`; the key is sent in a header and never appears in an error. `Refresh` matches the watched games without a match (`LookupAppID` from the game's `steam` link, else `LookupTitle`, accepted only when `SameTitle`: equal after lower-casing and dropping punctuation; the owner's choices, `source = 'user'`, are never searched again and an automatic "no match" is retried after a week), then reads the prices of the matched ones with `POST /games/overview/v2` in batches of 50 (current best price and lowest ever in one call) and stops at the first 429 keeping what it saved. Also `SetMatch`, `ClearMatch`, `SetCountry`, `Load`, `RefreshOne`.
- **`internal/hltb`**: the HowLongToBeat search client (`Search`, `ErrUnavailable`, `ErrChanged`); see section 8. Used only by `GET /api/hltb/search`.
- **`internal/posters`**: `Maker` (`Make`, `Choose`, `ChooseCrop`, `Remake`), `Queue` (the single background goroutine) and the `fetch-posters` command; see "Posters" in section 5.
- **`internal/covers`**: `Fetch` (importer) and `FetchStrict` (client URLs, no redirects), `Save` (decode, size guard, scale to at most 480px wide, write `<id>.jpg` atomically).

| `series.js`, `seriesview.js` | **pure** series grouping, progress counts and the "3 of 5" position (definitions of finished / played / left are in the header of `series.js` and in the user manual, section 12); plus the pure helpers of the "not registered" games (`missingIndex`, `shelfItems`, `fanGames`, `seriesSummary`); and the `#/series` page: the tile grid, and `#/series/<key>` as a poster shelf with Add and Hide (`seriesview.js`). It groups `store.games` by series name (case-insensitive), reads the server's cache from `GET api/series/missing` (polling it while a refresh runs) and redraws on `games-changed`. New requests there use relative URLs (`api/...`, `covers/...`) |
| `link.js`, `linkqueue.js` | the "Link with IGDB" review screen (route `#/link`; the navigation shows its link while the queue is not empty) and its **pure** logic (score tone, progress text, skipped games) |
| `ttbfilter.js` | the Time to beat block of the filter panel (quick ranges, From/Under, No time known, which estimate), shared by the Library and `gamepicker.js` |
| `platforms.js`, `ownership.js`, `years.js`, `colors.js` | pure helpers: IGDB platform mapping, ownership emojis, card year chips, colour maths |
| `util.js` | `h()` element builder, dialogs, toast, icons |

**State and events.** `store.games` is one array held in memory, mutated in place. Editing is **optimistic**: `patchGame` applies the change locally, then sends it; edits to one game are queued so a slow answer can never overwrite a newer edit; a failure restores the game from the server. Events on `window`:
- `games-changed` (`detail.id` = the game; `detail.reorder` when only positions moved): views rebuild only that card and refresh counts. If a new filter value appeared (a new genre, platform, year...) the library asks for a full rebuild.
- `games-reloaded`: a game was added or deleted; the router re-renders the page.
- `views-changed`: saved views changed; the navigation is rebuilt.

**Formats**
- Saved view `filter`: `{"q": "", "in": {"genre": ["RPG", "Indie"]}, "ex": {"status": ["finished"]}, "all": ["genre"], "flags": ["favorite"]}`. Facet keys: `status, platform, genre, theme, year, ownership, mode, perspective, player`; flags: `favorite, vr, completed`. Time to beat: `"ttb": {"min": 300, "max": 900, "unknown": "in", "kind": "ttb_hastily"}` (all optional, minutes; `min` inclusive, `max` exclusive; `unknown` is `in` = also/only games with no time, `ex` = hide them; `kind` is empty for `ttbMinutes` or one of the `ttb_*` columns, which then has no fallback). The UI is `ttbfilter.js`, shared by the Library and the rankings' game picker. The old `short` flag is migrated on load to `ttb.max = 600` (JSON and URL), so a saved view is rewritten with the range the next time it is saved. In the URL: `ttb_min`, `ttb_max` (minutes), `ttb_unknown`, `ttb_kind`.
- `sort`: `[{"field": "status", "dir": "asc"}, ...]` (fields in `SORT_FIELDS`); `group_by`: a key of `GROUP_FIELDS` or `""`; `layout`: `cards` or `table`.
- The Library (not a saved view) keeps the same state in the URL query, e.g. `#/library?genre=RPG&ex_status=finished&all=genre&sort=title:asc&layout=table`.

**Table.** Rows have a fixed height; only the visible ones exist in the DOM (`paint`). Each row remembers a signature of what it shows, so a refresh rebuilds only rows whose data changed (a click that started on an unchanged row still completes). The row being edited is never destroyed by a refresh. Column widths and visibility are kept in `localStorage` (a per-device convenience).

**Relative URLs (served at `/` or under a sub-path).** The app works both at the root (`http://deltabacklog.local/`) and behind a reverse proxy that serves it under a prefix and strips it (`http://<pi-name>.local/backlog/`), with no setting: every URL the frontend builds is relative to the page. `api.js` fetches `api/games`, covers are `covers/<file>?v=...`, the server answers screenshot `src`/`thumb` as `screenshots/<id>/<file>`, `main.js` registers `sw.js` (so its scope is the folder the page is in), the manifest has `start_url` and `scope` `./`, and routing is hash based (`#/library`), so the page URL itself never changes. The page must be loaded with its trailing slash (`/backlog/`, the proxy redirects `/backlog`). **Rule: never write a root-relative URL (`'/api/...'`, `'/covers/...'`) in the frontend**; `TestFrontendURLsAreRelative` (`web/web_test.go`) fails on one. The Go server is unchanged: it always serves at `/` and does not know the prefix.

**Service worker (`sw.js`).** All its paths are relative to `BASE`, the folder of the worker's own URL (`/` or `/backlog/`); it ignores requests outside it. Under a sub-path the cache names start with the base path (`/backlog/shell-v42`), because Cache Storage is shared by the whole origin and another app may live at its root; at `/` the names are the plain ones below. Network first for the app shell and the API (the cache is only an offline fallback), cache first for `covers/*` (their URLs carry the cover version; the `covers-v2` cache holds one entry per cover file, keyed by path, so a new version replaces the old one, and an older entry is served only when the network fails), never cache `GET /api/screenshots` (every search and page is another URL), cache first for screenshot **thumbnails** only (`*_t.jpg`, newest 400 kept); an original under `screenshots/` is never cached (the worker does not answer it). **Rule: bump `VERSION` whenever any shell file changes (HTML, CSS or a module), and add every new module to `SHELL_FILES`**; a stale `VERSION` leaves old clients on the old cache. Both are easy to forget when adding a page; `TestServiceWorkerCachesTheWholeShell` (`web/web_test.go`) fails when a module is missing from `SHELL_FILES` (the `VERSION` bump is still on you). The server sends `Cache-Control: no-cache` for the shell.

**Style.** `styles.css` uses CSS variables for light and dark (`prefers-color-scheme`, with a `data-theme` override). Breakpoints: below 600px phone layout, from 900px sidebar plus filter panel.

## 8. External services

- **IGDB** (Twitch client credentials, token cached): game details, candidate search, artworks and screenshots. Its genre names are what the library already uses. `platforms.js` maps IGDB platform names onto the library's names and pre-selects the platform the library has the most games on.
- **IGDB sync (phase 1: link every game).** `deltabacklog sync-igdb [--dry-run] [--db path] [--limit n]` (reads the keys from `.env`; the database defaults to `$DATA_DIR/app.db`). It searches IGDB by title for each game with no `igdb_id`, no earlier search and no "not on IGDB" mark, and buckets the answer (section 6). *Confident* matches set `igdb_id` and `igdb_synced_at`; *uncertain* ones are stored in `sync_candidate` for the review screen; every searched game gets `igdb_checked_at`, in the same transaction as its outcome, so a stopped run (Ctrl-C, repeated 429s, no network) simply continues next time. A confident match whose IGDB id another game already has goes to review instead (`igdb_id` is unique). A failed search leaves the game unchecked, so it is tried again. `--dry-run` copies the database with `VACUUM INTO` into a temporary folder (opened read-only, so an unmigrated file is not migrated), runs on the copy, prints a report (counts and examples per bucket) and deletes it: the database file is never written. A real run first writes a full backup, `app-before-igdb-link-<time>.db`, next to the database; **every** run does, including each `--limit` run, so mind the SD card. Pacing: the meta client sends at most 4 IGDB requests per second (250 ms between requests, shared by everything using the client). A title takes 2 requests (3 when it ends in a year, more when the fallback queries run), so expect about 2 titles per second at best: roughly 10 to 15 minutes for 600 games. Restart the server afterwards: it caches `/api/games`, and the command runs in another process. Phase 1 stores nothing but the link; phase 2 (next item) reads the details. IGDB scores are never fetched or stored (owner decision).
- **IGDB sync (phase 2: enrich the linked games).** `deltabacklog sync-igdb --enrich [--dry-run] [--refresh] [--db path] [--limit n]`. For every game with an `igdb_id` and no `igdb_enriched_at` it asks IGDB, 20 games per request (`where id = (...)`), for the facts (`/games`: release date, genres, themes, platforms, developer, collection, game modes, player perspectives, website URLs) and for `/game_time_to_beats` (seconds; stored as minutes, rounded). **Fill only empty fields:** release year, developer, genres, themes, series and platform are written only while the game has none (the owner's values are never changed, and a lookup row such as a company or series is created only when a value is actually written, so IGDB's spelling never lands next to the owner's). The platform is filled only when IGDB names exactly one (a game's platform is where the owner has it, not where it was released) *and* it resolves to a platform the library already has through `PlatformKey` (the Go twin of `web/static/js/platforms.js`; the two alias tables must stay in sync, `TestPlatformAliasesMatchTheJS` checks it); the enrichment never creates a platform, and the report counts the ones it left. **Series** (`enrich_lookup.go`): IGDB names a collection after almost every standalone game, so a collection is used only when its folded name (`meta.FoldKey`: case, accents, `&` = `and`, letters and digits) equals a series the library has (the owner's spelling is kept), or when at least two library games share it (a pass after the batches, over every enriched game, so it also completes pairs across runs; IGDB's name is kept in `igdb_series` for that). Franchises are never used (they are not even requested). A `PATCH` that carries `series` (any value, also `""`) sets `igdb_series` to NULL: the owner has decided, and the pass never touches that game again. The report counts the series set on games read in this run ("series") separately from those set on games of earlier runs because a game read now completed their collection (`SeriesCompleted`). The other proposals are only listed in the report. **Plausibility:** a time over 1000 h is stored as NULL, and a game whose quick/usual/complete times contradict each other (quick > usual > complete) gets none. **New data** (time to beat, modes, perspectives, store links) is IGDB's: a later `--refresh` run re-reads the already enriched games and replaces **only** this data (a time IGDB no longer reports is kept); it never fills year, developer, genres, themes, platform or series, because a field the owner emptied on purpose looks like one that was never set. Store links are recognised by host (Steam, GOG, Epic) or IGDB's `official` website type, http(s) only, one per kind. A batch is written in one transaction together with its `igdb_enriched_at` marks, so a stopped run (Ctrl-C, 429s, no network) continues where it stopped; a failed request leaves its games unmarked (5 failures in a row stop the run); a linked game IGDB no longer returns is marked done and counted as missing. Pacing: 250 ms between requests (a batch is two requests, so about 4 requests per second at most), one goroutine, doubling backoff from 2 s on 429, or IGDB's `Retry-After` (up to a minute) when it sends one (6 retries, then the run stops, resumable). `--dry-run` works on a temporary `VACUUM INTO` copy like phase 1 (inside one transaction that is rolled back, so the series pass sees the whole run) and prints counts of what would be filled; a real run first writes `app-before-igdb-enrich-<time>.db` next to the database (every run does). `updated_at` is not touched. Restart the server afterwards (it caches `/api/games`). Nothing about scores is requested; `meta/enrich_test.go` fails if a query mentions rating, hypes, follows or score. The enrichment also stores each game's IGDB collection id (`game_collection` and `game.igdb_parent_id`, IGDB's own data, rewritten on `--refresh` too), and a real (not dry) run that was not stopped ends by calling `collections.Refresh` with the same client (it prints "Reading the IGDB collections of your series..." and a one-line summary; the covers go to `covers/` next to the database): see "Series collections" in section 5.
- **HowLongToBeat** (`internal/hltb`, no key, no official API). The client does what the site's own search box does: `GET /api/search/site/init?t=<ms>` returns a short-lived `token`, then `POST /api/search/site` with the `x-auth-token` header, a browser User-Agent, a `Referer` of the site and a JSON body (`searchType: "games"`, the title split into `searchTerms`, `searchOptions`). The answer's `data[]` gives `game_name`, `game_type` (only `game` is kept), `release_world`, and `comp_main`, `comp_plus`, `comp_100` in **seconds** (stored as minutes); the scores and counts in the same answer are dropped on parse. The host is fixed; `BaseURL` is overridable only in tests. A 403 refreshes the token once; searches are spaced at least a second apart; the HTTP timeout is 8 s (the site can be slow, or blocked by some ISPs). Failures are `ErrUnavailable` (network, timeout, refusal, rate limit) or `ErrChanged` (404/410/405, or an answer without the expected shape), and the API turns them into a 502 message. **Expect it to break:** the endpoint path, the token handshake and the body have changed several times upstream. When it does, re-read the site's search code (the Next.js chunk that calls `/api/search/site`) and adjust `hltb.go`; nothing else depends on it, and the times can always be typed. Live check: `DELTABACKLOG_LIVE=1 go test ./internal/hltb -run TestLive -v` (rarely: it is not an API to hammer).
- **SteamGridDB**: `search/autocomplete` for the best (exact-title preferred) match, then `grids/game/{id}` with `dimensions=460x215,920x430`, falling back to any shape. For rankings, `SteamGridPortrait` asks for `dimensions=600x900` and takes the first grid; IGDB's `IGDBCoverURL` reads only `cover.image_id` (one small query) and builds the `t_cover_big_2x` URL.
- **Steam** (`appdetails`, no key): used only by the link resolver.
- **IsThereAnyDeal** (API v2, key in the `ITAD-API-Key` header; docs at docs.isthereanydeal.com): `GET /games/lookup/v1?appid=|title=`, `GET /games/search/v1`, `POST /games/overview/v2?country=&vouchers=false` (body: up to 200 game ids; the client sends 50). The limit is 1000 requests per 5 minutes with a `Retry-After` on 429. Matching costs one or two lookups per game without a match (the first run and each game added later; at the 400 ms pacing 300 games take about four minutes and stay far under the limit), the prices about one request per 50 games, and the page never calls ITAD on load.

## 10. Workflow

- Branches: `main` plus `features/<name>`; changes reach `main` through pull requests with merge commits, never by committing to `main`.
- **Do not stack a PR on another unmerged PR for long.** A PR merged into its base branch is not in `main` (this has happened); merge each PR into `main` and branch the next one from `main`.
- Commit messages: a short summary line, a body saying what and why, and the `Co-Authored-By` line given by the session.
- **Secrets** (IGDB and SteamGridDB keys) live only in `.env`. `git grep` for keys before pushing.
- A change in behaviour updates the matching section of the **user manual** and, if it touches structure, the API or the data model, the **developer manual**, in the same PR.

## 11. Build and deploy

The program is **cross-compiled on the PC** and uploaded; the Pi never holds the source and never builds anything (compiling the SQLite library needs most of a 1GB Pi and minutes of CPU, which would starve the other services). It runs directly under **systemd**, with no container, to keep the memory use at about 15MB.

**Deploy or update (from the PC, Go on PATH, `ssh raspberry` working, or `DEPLOY_HOST=user@host`):**

```sh
bash deploy/deploy.sh                       # build + upload + install; data and settings are kept
bash deploy/deploy.sh --seed <dir> --env .env   # first install: <dir> has app.db and covers/; --env installs the keys
```

`deploy.sh` builds `GOOS=linux GOARCH=arm GOARM=7 CGO_ENABLED=0` (version stamped from `git describe`), uploads to `/tmp/deltabacklog-deploy`, runs `install.sh` with sudo and deletes the upload. `install.sh` is idempotent: it never overwrites an existing database, restarts the service only when the program (or settings) changed, and waits until `/healthz` answers. When the program changed and a database exists, it first writes `/var/backups/deltabacklog/app-before-upgrade-<time>.db` (with the new binary, as the service user; `backup` never migrates, so this is the database as the old version left it), because the new version may migrate the database when it starts; if that backup fails, the program is not replaced. These copies are pruned with the nightly ones after 14 days.

**What is on the Pi**

| Path | What |
|---|---|
| `/opt/deltabacklog/deltabacklog` | the program; `backup.sh` next to it |
| `/var/lib/deltabacklog/` | the data: `app.db`, `covers/` (owner `deltabacklog`, mode 750) |
| `/var/backups/deltabacklog/` | nightly backups `app-YYYY-MM-DD.db`, last 14 days; `screenshots/` is the incremental copy of the screenshots (never pruned) |
| `$SCREENSHOTS_DIR` (default `/var/lib/deltabacklog/screenshots`) | the screenshots; on an external drive, for example `/mnt/drive/deltabacklog/screenshots` (next to a `backups/` folder) |
| `/etc/deltabacklog.env` | settings and the IGDB / SteamGridDB keys (root only, mode 600); `ALLOWED_HOSTS=name1,name2` goes here when the app is reached by a name other than `deltabacklog.local`, an IP address or the Pi's hostname (otherwise 421 "unknown host"); `PUBLIC_NAME=off` turns the friendly address off (below); restart the service after editing. A `deploy.sh --env` replaces the file but keeps `SCREENSHOTS_DIR`, `ALLOWED_HOSTS` and `PUBLIC_NAME`, and with `PUBLIC_NAME=off` also `LISTEN_ADDR` (`merge_settings` in `install.sh`) |
| `/etc/systemd/system/deltabacklog.service`, `deltabacklog-backup.service`, `deltabacklog-backup.timer`, `deltabacklog-name.service` | the units (sources in `deploy/`) |

**Starting at boot.** `deltabacklog.service` is enabled (`WantedBy=multi-user.target`) with `Restart=always` (a crashed process is back in about 4 seconds, tested with `kill -9`). It runs as the unprivileged system user `deltabacklog` with `NoNewPrivileges`, a read-only file system except its data folder, and `Nice=5`. The Pi's kernel does not enforce systemd memory limits (the memory cgroup is off on Raspbian), so the real cap is `GOMEMLIMIT=96MiB` in the settings file.

**Friendly address (`http://deltabacklog.local`).** `deltabacklog-name.service` runs `/opt/deltabacklog/name.sh` (source `deploy/name.sh`), which does two things: it announces the name `deltabacklog.local` with `avahi-publish` (mDNS, pointing at the source address of the default route, `ip -4 route get 1.1.1.1`), and it keeps two `iptables` NAT rules that send port 80 to 8081. The PREROUTING rule matches only traffic **addressed to the Pi** (`-m addrtype --dst-type LOCAL`), so containers on the Pi going out to port 80 elsewhere are untouched; the OUTPUT rule covers the Pi's own requests to itself. The app still listens only on `:8081`. The rules are added when the unit starts and removed when it stops (`ExecStopPost`, which also removes the first version of the rule that had no address match), so they come back at every boot and disappear when the unit stops (for example `systemctl disable --now`; `disable` alone keeps them until the next boot). Anything else listening on port 80 on the Pi (for example another web UI) is shadowed for traffic addressed to the Pi.

`install.sh` installs `avahi-daemon`, `avahi-utils` and `iptables` with apt (running `apt-get update` first, only when something is missing), installs `name.sh` and the unit, and enables it. **Re-running it also updates the name unit**: when the unit file or `name.sh` changed it clears (for a changed `name.sh`, the old script removes its own rules first) the old rules and restarts the unit, otherwise it just makes sure it is running. This step is optional: if it fails the install still succeeds and prints a warning. **`PUBLIC_NAME=off`** in `/etc/deltabacklog.env` skips it: `install.sh` disables and stops `deltabacklog-name.service` instead (`systemctl disable --now`; its `ExecStopPost` removes the port 80 rules), so `deltabacklog.local` is no longer announced and port 80 is left to whatever else uses it; it also leaves `LISTEN_ADDR` alone (`name_off`, `name_unit`, tested in `deploy/scripts_test.go`). Without the setting nothing changes. Use it when the app is only reached through a reverse proxy, such as a dashboard's `/backlog/` path behind its login, together with `LISTEN_ADDR=127.0.0.1:8081` so that port 8081 is not reachable from the network either (the proxy and the install's health check use `127.0.0.1:8081`). Set both by hand (`sudo nano /etc/deltabacklog.env`), then run `install.sh` (or `deploy.sh`) again or `sudo systemctl disable --now deltabacklog-name.service && sudo systemctl restart deltabacklog`. The unit was first installed by hand on the maintainer's Pi, so the first deploy of this version replaces it (the old rule is removed by `name.sh rules-del`). Caveats: mDNS needs a client that understands `.local` (Windows 10+, macOS, iOS and Linux with avahi do; **some Android versions do not**, and then `http://<ip>:8081` is the fallback), and the name keeps the address it had when the unit started, so give the Pi a fixed IP in the router.

**Backups.** `deltabacklog-backup.timer` runs `backup.sh` every night at 03:30 (with `Persistent=true`, so a missed run happens at the next boot). It calls `deltabacklog backup <file>`, which uses SQLite's `VACUUM INTO` for a consistent copy while the app runs, never overwrites an existing file and writes under a temporary name. Covers are not backed up (they can be downloaded again).

```sh
ssh <user>@<pi-address>   # the same host you gave as DEPLOY_HOST
sudo systemctl start deltabacklog-backup.service            # a backup right now
sudo /opt/deltabacklog/deltabacklog check /var/backups/deltabacklog/app-2026-10-07.db   # integrity, schema version, counts (read-only)
# restore: stop, put the copy in place, fix the owner, start
sudo systemctl stop deltabacklog
sudo cp /var/backups/deltabacklog/app-2026-10-07.db /var/lib/deltabacklog/app.db
sudo rm -f /var/lib/deltabacklog/app.db-wal /var/lib/deltabacklog/app.db-shm
sudo chown deltabacklog:deltabacklog /var/lib/deltabacklog/app.db
sudo systemctl start deltabacklog
```

**Screenshots on the external drive.** The SD card is small; screenshots live on the hard drive. Put `SCREENSHOTS_DIR=/mnt/drive/deltabacklog/screenshots` in `/etc/deltabacklog.env` and run `deploy.sh` (or `install.sh`) again; a later `deploy.sh --env` keeps that line. `install.sh` is idempotent and does this: (1) writes the drop-ins `/etc/systemd/system/deltabacklog.service.d/screenshots.conf` (`ReadWritePaths=-<its parent>`, the drive's `deltabacklog` folder, which exists whenever the drive is mounted) and `deltabacklog-backup.service.d/screenshots.conf` (the same, because the backup also writes `<parent>/backups`), because `ProtectSystem=strict` leaves everything but the data folder read-only; the leading `-` makes a missing path harmless, and both drop-ins grant the drive's `deltabacklog` folder (the parent of the screenshots folder, which exists whenever the drive is mounted) rather than the screenshots folder itself; they also carry `After=<mount unit>` (from `systemd-escape --path --suffix=mount` of the mount point found by `findmnt`, mounted or in `fstab`), which only orders the start after the mount when both start at boot: there is **no** `Requires`/`Wants`/`RequiresMountsFor`, so the service still starts without the drive and answers "screenshot storage not available" until it is back (restart the service after mounting if it still says so; after a reboot, verify with `curl -s 127.0.0.1:8081/api/games/<id>/screenshots`, which must contain `"available":true`). When a drop-in is created or changes, `install.sh` restarts the service, also without `--env` or a new program; drop-ins are removed again when the folder is inside the data folder; (2) creates `<screenshots dir>` and `<parent>/backups` owned by `deltabacklog` **only when the folder and its parent are really on another mounted drive** (`on_other_mount`: `findmnt` must report a target other than `/`), so an unmounted drive's empty mount point on the SD card is never filled; it prints a warning instead. `SCREENSHOTS_DIR` must be a **folder inside the drive**: if it is the mount point itself (for example `/mnt/drive`), `install.sh` refuses and exits, because the `backups` folder would be created beside it, on the SD card. The app itself never creates `SCREENSHOTS_DIR` (see section 5). Move existing screenshots (none on the first install) with `rsync -a /var/lib/deltabacklog/screenshots/ /mnt/drive/deltabacklog/screenshots/` while the service is stopped.

**Backups with the drive.** Every night `backup.sh` does three things, and the last two never fail the database backup (a problem is logged and skipped): (1) the database copy in `/var/backups/deltabacklog` (SD card, 14 days); (2) when `SCREENSHOTS_DIR` is set and `<parent>/backups` exists, the same file there too, on the drive, 14 days, so a dead SD card does not take the database with it (the folder is never created by the script; `install.sh` makes it); (3) the screenshots: `deltabacklog backup-screenshots --min-free-gb N /var/backups/deltabacklog/screenshots` copies the files missing there, so the originals (drive) and the copy (SD card) are on **different devices**. Copies are never deleted, even for screenshots deleted in the app (retention is "forever"; disk use grows with the library: about the size of `<screenshots dir>`; clear `/var/backups/deltabacklog/screenshots` by hand if you do not want deleted pictures kept). The free-space guard lives in the Go subcommand (`backup.sh` passes `SHOTS_MIN_FREE_GB`, default 5, set it in `/etc/deltabacklog.env`): before each file it asks `statfs` (Linux only; elsewhere the check is skipped) for the free space of the backup disk and leaves the file when copying it would drop below the margin, with a log line at the end saying how many were left; smaller files that still fit are copied. Because it checks the files actually copied, pictures kept in the backup after being deleted in the app cannot make it underestimate. Restore after a lost SD card or a new install: install the program, put the database back (from the drive's `backups/` or the SD one) as in the steps above, set `SCREENSHOTS_DIR` to the drive's folder (the originals and thumbnails are intact there). The restored database may be older than some pictures on the drive: on the first start the sweep adds those pictures back (log line "re-adopted"), and never deletes them; pictures of games the restored database does not know are moved to `.orphans/<game id>/` on the drive. Lost the drive instead: stop the service, `cp -a /var/backups/deltabacklog/screenshots/. <new screenshots dir>/` (owner `deltabacklog`) and start it. To copy the pictures off the Pi: `rsync -a <pi>:/mnt/drive/deltabacklog/screenshots/ ./screenshots-backup/`.

**Day to day:** `journalctl -u deltabacklog -f` (log), `systemctl status deltabacklog`, `systemctl list-timers deltabacklog-backup.timer`.

**Never test against the Pi's real database.** For experiments copy `app.db` to a temporary folder and run a second instance on another port (this is how the write timings below were measured), then delete it.

**Under a sub-path behind a reverse proxy.** A proxy may publish the app as `http://<host>/backlog/` (see "Relative URLs" in section 7). It must strip the prefix before forwarding to `127.0.0.1:8081`, keep the original `Host` header (the guard checks it, and the cross-origin check compares it with `Origin`), and redirect `/backlog` to `/backlog/`. Add that host name to `ALLOWED_HOSTS` in `/etc/deltabacklog.env` (otherwise 421). Nothing changes in DeltaBacklog itself. When the proxy is the only way in, set `PUBLIC_NAME=off` and `LISTEN_ADDR=127.0.0.1:8081` (see "Friendly address" above). To try it locally, put a small `httputil.ReverseProxy` that strips the prefix in front of a test instance (never on port 8081).

**HTTP only, so no service worker on the Pi.** Browsers only allow service workers and "Install app" on HTTPS or `localhost`. Served as `http://deltabacklog.local` or `http://<pi-address>:8081` the app works fully, but the offline cache is inactive, and "Add to Home screen" creates a plain shortcut. Real installation needs HTTPS (for example a reverse proxy with a certificate); not set up.

**Performance (measured on the Pi 3B+ from the PC over the LAN, with a real browser)**

What makes it fast:
- The two big reads (`/api/games`, `/api/facets`) are built once, gzip-compressed once, kept in memory with an `ETag`, and rebuilt in the background 400ms after the last write (`internal/api/cache.go`; `Server.Warm`). Reads cost no database work; a repeat visit is a 304 without a body.
- Editing one game loads only that game's rows (`loadGames(d, id)`), not the whole library.
- Static files are compressed and fingerprinted once at startup (`web/web.go`), served with `no-cache` + `ETag` (new deploys show at once; repeat visits are 304s), and `index.html` is sent with a `modulepreload` link for every module so the browser fetches the scripts in parallel instead of one import level at a time.
- Covers load only when they are about to scroll into view (`lazyImg` in `util.js`, an `IntersectionObserver`). The browser's own `loading="lazy"` was not enough: Chrome requested all 599 covers (15MB) on every revisit or reload.

| | Before | After |
|---|---|---|
| `GET /api/games`, requests per second | 9 | about 1,500 (gzip) |
| `GET /api/games`, time per request | 136 ms (930 ms with 8 clients) | 1 to 10 ms |
| `GET /api/games`, bytes on the wire | 285 KB | 22 KB |
| first request after a restart or a write | 210 to 280 ms | 3 ms (warmed in the background) |
| repeat visit, whole page | 15.6 MB, 624 requests | 5 KB, 39 requests (304) |
| first card on screen: LAN / 4G-like phone / 3G-like phone (CPU throttled 4x) | 2.9 s / 0.9 s / 1.8 s | 0.18 s / 0.9 s / 1.8 s |
| edit (PATCH), create, reorder | | 7 to 25 ms |
| memory of the process | | about 15 to 19 MB |

Under a sustained load of 8 clients the Pi's CPU reaches its thermal limit; ordinary use is far below that.

## 12. Known gaps

- Games imported from NocoDB have no `igdb_id` until `deltabacklog sync-igdb` (or **Fill from IGDB**) links them; duplicate detection falls back to the title. Run `deltabacklog sync-igdb` then `deltabacklog sync-igdb --enrich` to fill in the rest; until then the game mode and perspective filters are hidden, the Time to beat filter has nothing to filter by, and the Stats page says it has no times.
- Not built yet: a JSON export.
- Posters need IGDB or SteamGridDB keys to be good: without them (or for a game neither knows) the poster is a crop of the small wide cover, which is blurry at full tile size. `deltabacklog fetch-posters --upgrade` replaces those after the keys are set or more games are linked. A poster can be chosen by hand (see "Posters chosen by the user" in section 5).
- The old `tier` and `tierlist_entry` tables are unused but not dropped (migration 010 only copies them).
- No authentication (intended: home network only) and no HTTPS (see section 11: no offline cache or app install on the Pi).
- The pasted-link resolver (Steam, GOG, Epic, IGDB pages) exists in the backend but is not offered in the UI; only Steam links were tried against the real site.
- HowLongToBeat has no official API; its client can break without notice (section 8). The times can always be typed.
- Deals are for one country at a time; prices of another country need a refresh after changing it. A game with no exact title match on IsThereAnyDeal needs a hand-picked match.
